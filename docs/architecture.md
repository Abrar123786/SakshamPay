# SakshamPay architecture (P-1 summary)

The full architecture document, with every diagram, is maintained here:
https://claude.ai/artifact/FyUo3DKWQ8jADLsmkNpsEP

This file records the decisions that implementation must follow.

## Shape

- Modular monolith: React + Vite + Tailwind (Vercel) → FastAPI + SQLAlchemy (Render) → PostgreSQL.
- Routers validate and delegate; services hold logic; repositories own queries; the fraud
  engine after feature extraction is pure functions.

## Transaction lifecycle

States: `INITIATED`, `ANALYSED`, `AWAITING_USER_ACTION`, `APPROVED`, `CANCELLED`,
`EXPIRED`, `FAILED`.

- Assessment runs synchronously inside `POST /api/v1/transactions`.
- The user acts through one endpoint, `POST /api/v1/transactions/{id}/actions`
  (`CANCEL` | `CONTINUE` | `VERIFY`).
- Only the Transaction service changes status. Nothing reaches `APPROVED` without a stored
  assessment and an explicit user action. HIGH risk requires `VERIFY` (step-up re-auth).

## Risk scoring (initial, configurable values)

- Rules R1–R6: new beneficiary 20, unusual amount 25, velocity 20, timing 10,
  device/session 15, behavioural deviation 15; rule score capped at 100.
- Isolation Forest anomaly `a = -score_samples(x)`, ranked against held-out normal data and
  mapped piecewise to 0–100. It is a rank of unusualness, not a fraud probability.
- Combined `S = round(0.6 × R + 0.4 × M)`; LOW 0–30, MEDIUM 31–65, HIGH 66–100.
- ML unavailable → rules only, LOW raised to MEDIUM.

## Data

Six tables: `users`, `beneficiaries`, `transactions`, `risk_assessments`, `alerts`,
`audit_logs`. Amounts in integer paise. `(user_id, idempotency_key)` is unique.

## Security

Argon2id password hashing; JWT HS256, 30-minute access token kept in `sessionStorage`
(no refresh token in v1); CORS allowlist; one error shape
`{"error": {"code", "message", "request_id"}}`; API docs disabled in production.

## P-3 implementation notes

- **System vs versioned routes.** `/`, `/health` (liveness) and `/health/ready` (readiness)
  are unversioned and live in `app/routes/system.py`. Every business router is added to
  `api_router` in `app/routes/__init__.py`, which is mounted once at `API_V1_PREFIX`.
  P-2 mounted the same health router at both `/health` and `/api/v1/health`; the duplicate
  was removed and the frontend now calls `/health` at the API origin.
- **Settings** (`app/core/config.py`): one class, profile chosen by `APP_ENV`; development
  defaults apply only to unset values; production rejects unsafe values at startup.
  `DATABASE_URL` and `JWT_SECRET_KEY` are `SecretStr`; logs use `database_url_masked`.
- **Database** (`app/database/session.py`): a `Database` object per app on
  `app.state.database`; lazy engine; `check_connection()` never raises; `DbSession`
  dependency rolls back on error and always closes. Missing configuration → 503
  `DATABASE_NOT_CONFIGURED`; connection failures and timeouts → 503 `DATABASE_UNAVAILABLE`.
- **Services commit explicitly**; the session dependency never auto-commits.

## P-4 implementation notes

Full schema: [`database-schema.md`](database-schema.md).

- Models in `app/models/` (one module per table, plus `enums.py` and `common.py`) on the
  shared `Base` from `app/database/base.py`.
- One risk assessment per transaction (unique `transaction_id`); assessments and audit logs
  are append-only in the ORM.
- `final_risk_score = round(0.6 × rule + 0.4 × ml)` is enforced by a CHECK constraint;
  rules-only rows have `final_risk_score = rule_score`. `compute_final_risk_score()` is the
  Python twin.
- Rule weights total 105 (open decision); `rule_score` is stored capped at 0–100.
- Beneficiary account references and UPI IDs are stored masked plus an HMAC fingerprint;
  the fingerprint key setting arrives with the beneficiary service.
- All foreign keys are `ON DELETE RESTRICT`; composite foreign keys enforce that payees,
  transactions and assessments linked together belong to the same user.

## P-5 implementation notes

Operations guide: [`database-operations.md`](database-operations.md).

- Migrations: `4f58d3769176` (six tables, autogenerated and reviewed) and `6c0d187b23c1`
  (append-only triggers on `audit_logs` and `risk_assessments`). `create_all()` is used only
  by the P-4 model tests.
- Repositories in `app/repositories/` flush inside savepoints and never commit; callers own
  the transaction. No delete methods. Known constraint violations become `AppError`
  subclasses (`app/repositories/errors.py`).
- `TransactionRepository.create_idempotent` is race-safe; `transition` enforces the P-1
  lifecycle (ANALYSED needs a stored assessment; APPROVED needs an approval method the
  assessment allowed); `version` gives optimistic locking; `get_for_update` gives row locks.
- `RiskAssessmentRepository` computes the final score itself with the approved formula.
- Identifiers are masked and fingerprinted by `app/utils/privacy.py` with
  `IDENTIFIER_HASH_KEY`; IP addresses are truncated before audit storage.
- Two database roles recommended: owner (migrations) and app (least privilege,
  `backend/scripts/grant_app_privileges.sql`).
- Seed data: `python -m seeds.dev_seed`, repeatable, refused in production.

## P-6 implementation notes

Guide: [`authentication.md`](authentication.md).

- `app/core/security.py`: Argon2id (argon2-cffi defaults) and HS256 JWTs with claims
  `sub`, `iat`, `exp` only; no fallback key (503 `AUTH_NOT_CONFIGURED`).
- `app/services/auth.py`: registration and login; identical `INVALID_CREDENTIALS` for every
  login failure with constant-work verification; P-1 lockout (5 failures, 15 minutes) via an
  atomic counter update; audit events and an `ACCOUNT_LOCKED` alert.
- `app/routes/dependencies.py`: `CurrentUser` (token checked before the database is touched;
  user must exist and be active). Future protected routers use it.
- No migration: the P-4 users table already had every needed column.

## P-8 implementation notes

Guide: [`frontend-authentication.md`](frontend-authentication.md). Frontend only; the P-6
API contract is unchanged.

- Token in `sessionStorage` (D12) via `src/services/tokenStore.js`, as `{ accessToken, expiresAt }`.
  Expiry is computed from `expires_in`. Passwords and the profile are never stored, and the
  JWT is never decoded in the browser.
- `apiClient` attaches the bearer token only to requests under `VITE_API_BASE_URL`. A 401
  on an authenticated request clears the session; network errors and 5xx keep it.
  `ApiError.cause` is sanitised (no request body or headers).
- `AuthProvider` is the single owner of auth state (`restoring`, `authenticated`,
  `unauthenticated`, `error`). The `RequireAuth` and `GuestOnly` guards protect routes.
  Routes: `/login`, `/register`, `/account`.
- Registration does not sign in: it redirects to `/login` with the email prefilled.
  10-digit Indian mobile numbers are sent as `+91…`.
- Gaps kept as decisions for later phases: there is no server-side logout or revocation
  (the backend has no logout endpoint) and no refresh tokens. The production CSP is a
  deployment requirement once the Render and Vercel domains are known.

## P-9 implementation notes

Guide: [`dashboard.md`](dashboard.md). This is the first backend feature since P-6. It
uses the existing layering (route → service → repositories) with no migration.

- `GET /api/v1/dashboard/summary` (`app/routes/dashboard.py`): `CurrentUser` and
  `Cache-Control: no-store`. It reports counts by stored status (all seven keys), the
  approved amount in paise, `awaiting_action` (`expires_at >= now`, the sweep's
  boundary) and all-time unread alerts, over a rolling 30-day window on `created_at`.
- The dashboard uses its own session (`ReadOnlyDbSession` in `app/database/session.py`),
  separate from the `DbSession` that `CurrentUser` uses. Its transaction starts with
  `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ, READ ONLY`. `DashboardService`
  refuses a read-write session and never commits.
  Three aggregate methods were added to `TransactionRepository`.
- Risk statistics, recent transactions and charts are deliberately absent. The stored
  assessments are seed samples, history is P-11, and Recharts is added only when there
  is real risk data to chart.
- Frontend:
  - top navigation (`SignedInNav`, `SIGNED_IN_NAV_ITEMS`) with a phone disclosure menu;
  - `DEFAULT_SIGNED_IN_PATH` changed to `/dashboard`;
  - `DashboardPage` with key figures, status breakdown, empty, loading and error states;
  - `dashboardService` validates the response, so malformed data is an error, not zeros.
